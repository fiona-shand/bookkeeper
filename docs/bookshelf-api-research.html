Spines, not covers

Every book API on the open web returns the front cover. Not one of them returns a spine. The shelf in your screenshot can't be fetched — it has to be generated, from page counts and cover colours. That single fact decides the whole architecture.

Below is that generation, running. Every spine is drawn from two numbers a free API will give you — page count and binding — plus one colour sampled from the cover art. Click a book to see the maths behind its width.

The constraint everything hangs off

I checked the four sources that matter — Open Library, Google Books, Hardcover and ISBNdb. All four serve cover images. None serves a spine image, and there is no general-purpose spine API anywhere: the only spine-specific work in the field is computer-vision research on recognising spines in shelf photographs, and a Xerox patent on synthesising spines for print. Nothing you can call.

What this means

Your app is not a book-data app with a shelf skin on top. It's a spine-rendering app that happens to fetch metadata. The interesting engineering is local: derive spine geometry from page count, derive spine colour from the cover, typeset the title vertically. The APIs are the easy, solved half.

The good news is that the two inputs you need are in the cheapest tier of every source, and they're both already in a Goodreads CSV export — so you can build the entire shelf offline before you ever wire up a network call.

Layer 1
Metadata

Search and metadata

This is the "what book is this" layer: the user types piranesi, you resolve it to a title, author, ISBN, page count and binding. Four real options, one obvious default.

Verified while researching this

Google Books without an API key falls back to a quota shared across everyone on your IP. I called it from this machine and got a flat 429 RESOURCE_EXHAUSTED — someone else had already spent the day's allowance. Anonymous calls will work on your laptop right up until they don't. Get a key on day one; it's free.

Dead ends, so you don't lose an evening

  • The Goodreads API is gone. Retired to new developers in late 2020 and switched off since. Every tutorial you'll find for it is dead. This is exactly why Hardcover exists.
  • Amazon Product Advertising API has real cover art but requires an Associates account with qualifying sales before it will issue credentials. Not viable for a personal project.
  • StoryGraph has no public API. CSV export only.
Recommendation

Open Library as the spine of the system, Google Books as the search box. Query Google when the user is typing (its relevance is worth the key), then store the ISBN and read everything else — covers, page counts, editions — from Open Library, which has no key, no quota anxiety and CC0 data you're allowed to keep. Add Hardcover later only if you want the social layer.

Layer 2
Covers

Getting the cover image

You need covers for two reasons: the front face when a book is pulled off the shelf, and — more importantly — as the source of the spine's colour.

Open Library Covers

No key, no signup, and it accepts the identifier you already have. The pattern is https://covers.openlibrary.org/b/$key/$value-$size.jpg, where key is one of isbn, oclc, lccn, olid or id, and size is S, M or L. 

https://covers.openlibrary.org/b/isbn/9781635575637-L.jpg

// ?default=false returns 404 instead of a blank placeholder —
// essential, or you cannot tell "no cover" from "grey cover"
https://covers.openlibrary.org/b/isbn/9781635575637-L.jpg?default=false

// append .json for cover metadata rather than the image
https://covers.openlibrary.org/b/id/12547191.json

Two rules worth respecting: send a User-Agent with your app name and an email — it triples your rate limit from roughly 1 to 3 requests a second — and don't crawl. They will block bulk harvesting. Fetch a cover once, on add, and cache it.

Google Books images

Covers arrive in the volume's imageLinks object (smallThumbnail through extraLarge, depending on the volume). Two practical fixes: the URLs come back as http so rewrite them to https or they'll be blocked as mixed content, and stripping the &edge=curl parameter removes the fake page-curl graphic Google overlays on the corner.

Do this once, not per render

Download the cover when a book is added, store it locally, and extract its colour in the same pass. Rate limits make on-the-fly fetching fragile, and a shelf of 300 books would fire 300 requests on every page load.

Layer 3
Spines

Synthesising the spine

This is the part with no API behind it, and it's where the project is won or lost. Three approaches, in ascending order of how good they look.

Approach A
Squash the cover

Scale the front cover into a narrow strip. Ten minutes of work, and it looks wrong immediately — cover art is composed for a 2:3 rectangle, so titles smear into illegible bands. Every shelf that looks cheap did this.

Approach B · recommended
Generate from colour + type

Fill with a colour sampled from the cover, add a left-to-right gradient to fake the spine's curve, and typeset title and author vertically. Reads like a real shelf at any zoom, and every input is free.

Approach C
B, in CSS 3D

Same spine as a face of a preserve-3d box, with the real cover as the front face. Pulling a book out rotates it to show the cover. Best UX, and a natural phase two once B works.

Spine width is real bookbinding maths

Printers calculate spine width as page count divided by PPI (pages per inch — how many printed pages stack to an inch), plus an allowance for the cover itself. Use the same formula and the variation across your shelf comes out physically correct: a 700-page paperback genuinely is three times the width of a 250-page one. 

// PPI varies by paper stock; these are sane averages.
// Allowance covers glue and cover stock — or boards, for hardcovers.
const BINDING = {
  hardcover:  { ppi: 440, allowance: 0.25, heightIn: 9.25 },
  trade:      { ppi: 500, allowance: 0.06, heightIn: 8.00 },
  massMarket: { ppi: 560, allowance: 0.05, heightIn: 6.75 },
};

const PX_PER_INCH = 34;

function spineGeometry(pages, binding = "trade") {
  const b = BINDING[binding] ?? BINDING.trade;
  const inches = pages / b.ppi + b.allowance;
  return {
    inches,
    width:  Math.max(14, Math.round(inches * PX_PER_INCH)),
    height: Math.round(b.heightIn * PX_PER_INCH),
  };
}

Height matters as much as width. Driving it off binding gives you a ragged top edge across the shelf, which is most of what makes the screenshot read as a photograph of books rather than a bar chart. Open Library exposes physical_format on editions; a Goodreads CSV has the same thing in its Binding column.

Colour, extracted once at import

Run the cover through node-vibrant or colorthief server-side when the book is added, and store the hex on the row. Vibrant is the better fit here because it returns semantically labelled swatches — DarkVibrant is usually the closest match to a real spine, since publishers darken spine stock relative to cover art. Then pick your text colour by luminance so light spines get dark type: 

function readableInk(hex) {
  const srgb = [1, 3, 5]
    .map(i => parseInt(hex.slice(i, i + 2), 16) / 255)
    .map(c => (c <= 0.03928 ? c / 12.92 : ((c + 0.055) / 1.055) ** 2.4));
  const L = 0.2126 * srgb[0] + 0.7152 * srgb[1] + 0.0722 * srgb[2];
  return L > 0.42 ? "#1A1A17" : "#F4F1E8";
}

The two details that sell it

First, the curve. A flat rectangle of colour reads as a UI element; a spine catches light down its rounded face. One gradient does the whole job — dark at both edges, bright just inside the left one: 

background-image: linear-gradient(to right,
  rgba(0,0,0,.34)      0%,
  rgba(255,255,255,.13) 16%,
  rgba(255,255,255,.05) 46%,
  rgba(0,0,0,.10)      78%,
  rgba(0,0,0,.34)     100%);

Second, the type. writing-mode: vertical-rl gives you the top-to-bottom reading direction used on British and American spines — worth knowing that most European spines read bottom-to-top, so this is a real choice rather than a default. Add white-space: nowrap with text-overflow: ellipsis and long titles truncate gracefully instead of wrapping into a mess.

Everything above is what's rendering at the top of this page — same formula, same gradient, same luminance test.

Layer 4
Import

Filling the shelf on day one

An empty bookshelf is a bad first run, and nobody adds 200 books by hand. The Goodreads CSV export is the standard migration path, and it happens to contain precisely the fields the spine renderer needs.

Date Read, Date AddedSort + statsChronological shelves, year-in-review.

One quirk to handle: Goodreads writes ISBNs as ="9780385474542" — an Excel formula wrapper — so strip =" and " before lookup. Rows are also frequently missing ISBNs entirely, which is your cue to fall back to a title + author search rather than dropping the book.

StoryGraph exports a similar CSV, and Hardcover can hand you a user's whole library over GraphQL if you'd rather sync than import.

Terms worth reading before you scale

None of this blocks a personal project, but the constraints differ enough to matter if it ever goes public.

  • Open Library — data is CC0, so you can store and reuse it freely. Covers come from mixed sources and carry no blanket licence, so treat caching them as fine for personal use and get advice before building a business on it. Don't crawl.
  • Google Books — the ToS asks for visible Google attribution and a link from each result to its Google Books page, and forbids charging users for an app built on the API without written permission. Fine for a personal shelf; a real constraint on a paid product.
  • Hardcover — free and generous, but the token is personal. Send a descriptive User-Agent, as their docs ask.
  • Cover art is publisher copyright regardless of who serves it. Displaying it for a book you're cataloguing is standard practice across every reading app; wholesale redistribution is not.

What I'd build

You already have the stack for this in muscle memory — the tracker in this repo is Next.js and Prisma, and it transfers directly. SQLite locally, one Book table, covers cached to disk.

The sequencing that de-risks it: start at layer 3, not layer 1. Hand-write a JSON array of fifteen books with page counts and hex colours, and get the shelf looking right. That's the part that decides whether the project is worth finishing, it needs no API key, no network and no database, and if the shelf looks good with fake data it will look good with real data. The demo at the top of this page is roughly that milestone, and it's an afternoon's work.

Then import a Goodreads CSV to fill it, and only then add live search against Google Books and covers from Open Library. Colour extraction with Vibrant is the last step — until it's in, a hand-picked palette per book works fine, and honestly sometimes looks better.
